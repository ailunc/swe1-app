# 理解这个投票应用

本项目以 Django 5.2 官方教程 Parts 1–4 为基础。下面说明源码怎样连接起来，方便实际运行、修改和解释。

## 一次投票经过哪些文件

1. 浏览器访问 `/polls/`。`mysite/urls.py` 把请求交给 `polls/urls.py`。
2. `IndexView` 从数据库取按发布时间排序的最近五道题，交给 `index.html`。
3. 点击题目进入 `/polls/1/`。`DetailView` 根据网址中的主键 `pk` 查找题目，`detail.html` 展示它的选项。
4. 表单把选项 ID 用 POST 发到 `/polls/1/vote/`。题目 ID 来自网址，选项 ID 来自表单。
5. `vote()` 查找这道题自己的选项，更新票数，然后重定向到结果页。
6. `ResultsView` 再从数据库读出结果，`results.html` 显示各选项的票数。

## 数据怎么存

`Question` 保存题目文字和发布时间。`Choice` 保存选项文字、票数，以及所属题目的外键。一个题目可以有多个选项，一个选项只属于一个题目。

`question.choice_set.all()` 查找这道题的所有选项。`on_delete=models.CASCADE` 表示删除题目时，关联选项也会删除。

本地使用 SQLite，方便启动；云端使用 PostgreSQL，避免把唯一一份投票数据放在可以替换的应用实例上。

`makemigrations` 生成描述数据库结构变化的文件；`migrate` 真正把变化应用到数据库。迁移文件要提交到 GitHub，本地数据库文件不用提交。

## 为什么投票要这样写

- `question.choice_set.get(...)` 限定选项属于当前题目，不能拿另一道题的选项 ID 来投票。
- 未选答案或选项无效时重新展示表单和错误提示，票数保持原样。
- `F("votes") + 1` 让数据库完成加一，避免两个同时到达的投票读取同一个旧值后互相覆盖。
- POST 会修改数据库，所以不能让普通 GET 请求投票。
- `{% csrf_token %}` 给表单加入 CSRF 防护；服务器会拒绝没有有效令牌的提交。
- 成功后使用重定向，刷新结果页不会再次提交上一张表单。

## 教程 Part 4 的通用视图

`ListView` 负责列表，`DetailView` 负责单个对象。这里的 `DetailView` 和 `ResultsView` 都读取一个 `Question`，但使用不同模板。

通用详情视图默认从网址参数 `pk` 读取主键，因此它们的路由写 `<int:pk>`。投票函数自己的参数叫 `question_id`，它的路由写 `<int:question_id>`。

## 部署配置在做什么

- `requirements.txt` 告诉服务器需要安装哪些 Python 包。
- `WSGIPath` 告诉 Elastic Beanstalk 从哪里启动 Django。
- `ALLOWED_HOSTS` 指定允许访问应用的域名，避免随意接受 Host 请求头。
- `DJANGO_SECRET_KEY` 参与签名等安全操作；生产密钥只放在私有环境配置中。
- `collectstatic` 收集 CSS 和 admin 静态文件；WhiteNoise 提供这些文件。
- `seed_polls` 创建示例题，重复运行不会清零票数。你可以在 admin 中添加自己的题目；不要反复修改种子题文字来管理现有数据。

## 你可以实际完成的修改

运行应用后，用本地 admin 添加一道你自己选的题目和几个选项，再验证投票结果。也可以改首页说明和配色。修改后运行 `python manage.py test`，查看自己的改动有没有破坏流程，再做一次真实的 Git 提交。
